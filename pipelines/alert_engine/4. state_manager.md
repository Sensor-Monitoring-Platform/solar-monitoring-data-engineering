# Part 4 — `state_manager.py`

Now we build the **sensor state manager**.

This component is critical because your Alert Engine is not merely checking:

```python
if value > threshold:
    alert()
```

It also needs to understand **what is happening to each sensor over time**.

For every `device_id`, we want to know:

* When was the last valid event?
* Is the sensor currently online?
* Is it suspected to be offline?
* Has it recovered?
* How many invalid events occurred?
* When did the current state begin?
* What was the last known reading?
* Are events arriving late/out of order?
* How many events have we processed?

---

# But there is an important correction

The above code demonstrates the **state-management mechanism**, but we need to be precise about how the production version should work.

Your metadata says, for example:

```yaml
vibration:
  sampling_frequency_seconds: 10
  offline_grace_period_seconds: 60
```

Therefore the engine should **not** have a hardcoded:

```python
if elapsed > 60:
```

Instead:

```text
device_id
     ↓
device metadata
     ↓
device_type
     ↓
sensor metadata
     ↓
offline_grace_period_seconds
```

So eventually we'll build:

```text
SensorEvent
    │
    ├── device_id
    └── device_type
             │
             ▼
      Sensor Configuration
             │
             ├── sampling frequency
             ├── warning threshold
             ├── critical threshold
             └── offline grace period
```

That keeps the entire Alert Engine **metadata-driven**.

# Why we need `last_event_timestamp`

This solves your batch-order problem.

Imagine the raw batch arrives like this:

```text
arrival order:

05:03
05:01
05:04
05:02
05:05
```

We should **not** assume arrival order represents sensor chronology.

Instead:

```text
event.timestamp
```

is the sensor's event time.

The state manager keeps:

```text
last_event_timestamp = 05:05
```

If an old event arrives:

```text
05:02
```

we detect:

```python
event.timestamp < state.last_event_timestamp
```

and mark:

```text
out_of_order = True
```

We don't allow the stale event to overwrite the latest state.

# Why `last_received_at` is also important

This is a subtle but very useful distinction.

We have two different concepts:

### Event time

```text
timestamp
```

When the sensor says the reading happened.

### Processing/arrival time

```text
received_at
```

When our Alert Engine actually received the event.

These are **not necessarily the same**.

For example:

```text
Sensor reading:
05:00:00

Network delay:
12 seconds

Alert Engine receives:
05:00:12
```

Therefore:

```text
event timestamp  = 05:00:00
received_at       = 05:00:12
```

This later lets us calculate:

```text
processing latency = received_at - event timestamp
```

which will become one of your future performance metrics.

# The offline state machine

I recommend this model rather than immediately going:

```text
ONLINE → OFFLINE
```

because temporary delays are common.

```text
                 no event
              grace exceeded
                    │
                    ▼
               SUSPECTED_OFFLINE
                    │
              still no event
                    │
                    ▼
                 OFFLINE
                    │
               event arrives
                    │
                    ▼
                RECOVERED
                    │
                    ▼
                 ONLINE
```

This avoids generating an immediate "sensor dead" alert because of a tiny ingestion/network delay.

# Example: vibration sensor

Your metadata:

```yaml
vibration:
  sampling_frequency_seconds: 10
  offline_grace_period_seconds: 60
```

Suppose:

```text
10:00:00 → reading
10:00:10 → reading
10:00:20 → reading
```

Then nothing arrives.

At:

```text
10:00:21
```

nothing happens.

At:

```text
10:00:50
```

nothing happens.

At:

```text
10:01:00
```

the grace period is reached.

At:

```text
10:01:21
```

the engine can transition:

```text
ONLINE
   ↓
SUSPECTED_OFFLINE
```

If still nothing arrives:

```text
10:02:21
```

then:

```text
SUSPECTED_OFFLINE
   ↓
OFFLINE
```

And if a reading finally arrives:

```text
10:02:25
```

then:

```text
OFFLINE
   ↓
RECOVERED
   ↓
ONLINE
```

The **Alert Manager** will later decide which of these transitions actually produces an alert.

# Very important: state manager ≠ alert manager

We should keep these separate.

For example:

```text
State Manager:

TEMP-001
ONLINE → SUSPECTED_OFFLINE
```

This does **not itself send a WebSocket message**.

Instead:

```text
State Manager
      │
      ▼
StateUpdateResult
      │
      ▼
Alert Manager
      │
      ├── create alert
      ├── suppress duplicate
      ├── resolve existing alert
      └── publish event
```

This separation will make the system much easier to maintain.

# Where the missing-data calculation belongs

You mentioned:

> "if 60% values are missing then sensor might be malfunctioned"

That's slightly different from **offline detection**.

We should eventually have **two separate mechanisms**.

### 1. Offline detection

Based on elapsed time:

```text
Expected reading every 10 sec
Grace = 60 sec

No reading for >60 sec
→ OFFLINE
```

### 2. Data completeness / missing-rate detection

Based on a time window:

```text
Last 10 minutes:

Expected readings = 60
Received readings = 22

Missing = 38

Missing percentage = 63.3%
```

Then:

```text
63.3% missing > configured threshold
```

could produce:

```text
SENSOR_DATA_DEGRADED
```

These should **not be conflated**.

A sensor might technically still be online:

```text
reading every 40 seconds
```

but have terrible data completeness when it is expected every 10 seconds.

## One more architectural decision we'll make next

We should **not** write a giant chain like:

```python
if temperature > ...
elif vibration > ...
elif pressure > ...
elif smoke > ...
elif current > ...
...
```

Instead, the next major component should be the **metadata-driven Rule Engine**.

It will turn your existing `sensors.yml` into executable rules:

```text
temperature_process
    warning_high = 190
    critical_high = 210

vibration
    warning_high = 7
    critical_high = 10

pressure
    warning_high = 9
    critical_high = 10.5

smoke_alarm
    warning_high = 100
    critical_high = 200
```

Then one generic evaluator can process **every sensor type** without hardcoding sensor-specific `if/else` blocks.

That is where this starts becoming a genuinely **metadata-driven industrial monitoring architecture** rather than just a Python script full of conditions.
