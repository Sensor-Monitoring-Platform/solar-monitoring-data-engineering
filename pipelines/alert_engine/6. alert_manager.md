# Part 5 — `alert_manager.py` — Alert Lifecycle

Now we move to the **core incident-management layer**.

We already have:

```text
Sensor Event
    ↓
Rule Engine
    ↓
State Manager
    ↓
Deduplication
    ↓
🔥 Alert Manager
```

The `AlertManager` is responsible for turning a rule-engine decision into a **real alert/incident with a lifecycle**.

---

## 1. What AlertManager should do

It should answer:

> Given this event and the rule-engine decision, should I create a new alert, update an existing alert, acknowledge it, resolve it, or ignore it?

It should **not** decide whether `220°C` is dangerous.

That has already been decided by the rule engine.

For example:

```text
temperature = 220°C

Rule Engine
    ↓
rule_id = TEMP_PROCESS_CRITICAL_HIGH
severity = CRITICAL
triggered = true
```

Now AlertManager takes over:

```text
Is there already an active alert
for this sensor + rule?

        │
   ┌────┴────┐
   │         │
  NO        YES
   │         │
   ▼         ▼
CREATE     UPDATE
```

---

# 2. Alert lifecycle

We'll use:

```text
OPEN
  │
  │ operator acknowledges
  ▼
ACKNOWLEDGED
  │
  │ condition clears
  ▼
RESOLVED
```

There is an important distinction:

### OPEN

The alert exists and requires attention.

### ACKNOWLEDGED

An operator has seen/accepted responsibility for the alert.

It **does not mean the problem is fixed**.

### RESOLVED

The underlying condition has returned to a safe state.

# 3. Example

Suppose:

```text
TEMP-GGN01-L01-MC01-001
```

reports:

```text
220°C
```

Rule engine:

```text
TEMP_PROCESS_CRITICAL_HIGH
CRITICAL
```

AlertManager creates:

```json
{
    "alert_id": "ALT-000001",
    "device_id": "TEMP-GGN01-L01-MC01-001",
    "machine_id": "MC-ASM-01",
    "rule_id": "TEMP_PROCESS_CRITICAL_HIGH",
    "severity": "CRITICAL",
    "status": "OPEN",
    "first_seen": "...",
    "last_seen": "...",
    "current_value": 220.0,
    "peak_value": 220.0,
    "occurrence_count": 1
}
```

Then another event arrives:

```text
225°C
```

We **do not create another alert**.

Instead:

```json
{
    "alert_id": "ALT-000001",
    "current_value": 225.0,
    "peak_value": 225.0,
    "occurrence_count": 2
}
```

Then:

```text
230°C
```

becomes:

```json
{
    "alert_id": "ALT-000001",
    "current_value": 230.0,
    "peak_value": 230.0,
    "occurrence_count": 3
}
```

# 4. Data model

Create:

```text
alert_engine/
└── alert_manager.py
```

We'll first define the models.

```python
from __future__ import annotations

from dataclasses import dataclass
from datetime import datetime
from enum import Enum
from typing import Optional
import uuid


class AlertStatus(str, Enum):
    OPEN = "OPEN"
    ACKNOWLEDGED = "ACKNOWLEDGED"
    RESOLVED = "RESOLVED"


class AlertSeverity(str, Enum):
    INFO = "INFO"
    WARNING = "WARNING"
    CRITICAL = "CRITICAL"


@dataclass
class Alert:
    alert_id: str

    device_id: str
    device_type: str

    plant_id: str
    machine_id: str

    rule_id: str
    rule_type: str

    severity: AlertSeverity
    status: AlertStatus

    first_seen: datetime
    last_seen: datetime

    current_value: Optional[float]
    peak_value: Optional[float]

    unit: Optional[str]

    occurrence_count: int

    acknowledged_at: Optional[datetime] = None
    acknowledged_by: Optional[str] = None

    resolved_at: Optional[datetime] = None

    resolution_reason: Optional[str] = None
```

# 5. Why we store `first_seen` and `last_seen`

These are extremely important for later analytics.

Suppose:

```text
first_seen = 10:00:00
last_seen  = 10:17:30
```

We can calculate:

```text
incident_duration
=
last_seen - first_seen
```

Later this becomes useful for:

* machine reliability
* MTTR
* alert frequency
* sensor behaviour
* production downtime
* anomaly analysis
* AI evaluation

---

# 6. Why `peak_value`?

Suppose:

```text
220
225
240
270
250
230
```

We don't want to lose the maximum observed value.

So:

```text
current_value = 230
peak_value    = 270
```

This becomes particularly useful for critical incidents.

# 8. One correction to our earlier architecture

There is an important architectural point here.

We previously said:

```text
Deduplication
      ↓
AlertManager
```

Conceptually that's correct, but in the implementation the responsibilities are intertwined.

A cleaner orchestration is:

```text
                    Event
                      │
                      ▼
                 Rule Engine
                      │
                      ▼
                Rule Result
                      │
                      ▼
               AlertManager
                      │
                      ▼
              Deduplication check
                  /          \
                NEW          EXISTING
                 │              │
                 ▼              ▼
              CREATE          UPDATE
```

So **AlertManager orchestrates the incident**, while `AlertDeduplicator` is a service it uses.

This is cleaner than making the deduplicator responsible for creating/updating alerts.

---

# 9. What happens for every incoming event?

For a triggered event:

```python
result = deduplicator.check(...)
```

If:

```text
NO_EXISTING_ALERT
```

then:

```python
alert_manager.create_alert(...)
```

If:

```text
ACTIVE_ALERT
```

then:

```python
alert_manager.update_alert(...)
```

If the rule engine says the condition has cleared:

```python
alert_manager.resolve(...)
```

So the orchestration will eventually look roughly like:

```python
dedup_result = deduplicator.check(
    device_id=event.device_id,
    rule_type=rule_result.rule_id,
    severity=rule_result.severity,
    event_timestamp=event.timestamp,
)

if not rule_result.triggered:

    # Existing incident may need resolution
    ...

elif not dedup_result.is_duplicate:

    alert = alert_manager.create_alert(
        event=event,
        rule_result=rule_result,
    )

else:

    alert = alert_manager.update_alert(
        existing_alert,
        event=event,
    )
```

We'll clean this up properly in `main.py`.

# 10. Important: AlertManager does NOT write to the database yet

Right now:

```python
self._alerts
```

is only in memory.

That's intentional.

The next component is:

```text
alert_store.py
```

which will replace this temporary storage architecture with persistence.

The final architecture will be:

```text
                    AlertManager
                         │
                         ▼
                    AlertStore
                    /        \
                   /          \
             PostgreSQL      Cache
```

For our project, we can initially use something lightweight such as **SQLite** locally, while keeping the interface database-agnostic so we can later move to PostgreSQL.

---

# 11. Why not directly write every event to DB?

Because your original concern was **high-volume processing**.

Imagine:

```text
1,000,000 sensor events
```

and every event performs:

```text
INSERT → DB
INSERT → DB
INSERT → DB
...
```

That's unnecessarily expensive.

Instead, we distinguish:

### Sensor events

Potentially millions:

```text
220
221
222
223
224
...
```

### Alert incidents

Potentially much fewer:

```text
ALT-001
```

The alert record gets updated rather than creating a new alert every time.

We can later introduce asynchronous persistence/batching if required.

# 12. What happens with WebSockets?

Not here.

The responsibility separation is:

```text
AlertManager
      │
      ├──────► AlertStore
      │
      └──────► EventPublisher
                       │
                       ▼
                  WebSocket
```

So AlertManager shouldn't know that the frontend uses WebSockets.

It should simply emit something like:

```python
AlertCreatedEvent
AlertUpdatedEvent
AlertAcknowledgedEvent
AlertResolvedEvent
```

The next layers will handle persistence and real-time delivery.
