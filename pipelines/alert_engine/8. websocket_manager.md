# Part 7 — `websocket_manager.py` — Real-Time Alert Delivery

Now we connect the Alert Engine to the frontend.

The key architectural principle is:

> **WebSocket is the delivery mechanism, not the alert-processing mechanism.**

The alert engine should **never wait for the frontend** to process a sensor event.

The flow should be:

```text
Sensor Event
     │
     ▼
Rule Engine
     │
     ▼
Alert Manager
     │
     ├──────────────► AlertStore
     │                    │
     │                    ▼
     │                 Database
     │
     └──────────────► Event Publisher
                          │
                          ▼
                     WebSocket
                          │
                          ▼
                       Frontend
```

If the frontend is disconnected, **the alert must still be created and persisted**.

---

# 1. Why WebSockets?

Your requirement is real-time:

```text
Sensor reading
     ↓
Critical condition detected
     ↓
Alert generated
     ↓
Frontend immediately shows:
🔥 CRITICAL
Machine: MC-LAM-05
Sensor: TEMP-GGN01-L02-MC05-001
Value: 225°C
```

Polling would mean:

```text
Frontend
   ↓
"Any new alerts?"
   ↓
Backend
   ↓
"No"
   ↓
wait
   ↓
"Any new alerts?"
```

That introduces unnecessary latency.

WebSockets provide:

```text
Backend
   │
   │ push
   ▼
Frontend
```

---

# 2. But don't put WebSockets inside the Rule Engine

Avoid this:

```python
if temperature > 210:
    websocket.send(...)
```

That creates a dangerous coupling:

```text
Rule Engine
    ↓
WebSocket
```

Now your rule engine knows about the frontend.

Instead:

```text
Rule Engine
     ↓
AlertManager
     ↓
Alert Event
     ├──────────────► Database
     │
     └──────────────► WebSocket
```

This means you can later replace WebSockets with:

```text
Kafka
Redis Streams
RabbitMQ
Azure Event Hubs
```

without rewriting the rules.

# 5. `websocket_manager.py`

Create:

```python
from __future__ import annotations

import asyncio
import json
import logging
from typing import Any

from fastapi import WebSocket


logger = logging.getLogger(__name__)


class WebSocketManager:
    """
    Manages active WebSocket connections and broadcasts
    alert events to connected frontend clients.

    Important:
        This class is responsible ONLY for event delivery.

        It does not:
        - evaluate sensor rules
        - create alerts
        - resolve alerts
        - persist alerts
        - perform deduplication
    """

    def __init__(self) -> None:

        self._connections: set[WebSocket] = set()

        self._lock = asyncio.Lock()

    # ==========================================================
    # CONNECTION MANAGEMENT
    # ==========================================================

    async def connect(
        self,
        websocket: WebSocket,
    ) -> None:

        await websocket.accept()

        async with self._lock:
            self._connections.add(websocket)

        logger.info(
            "WebSocket client connected. "
            "Active clients=%d",
            len(self._connections),
        )

    async def disconnect(
        self,
        websocket: WebSocket,
    ) -> None:

        async with self._lock:
            self._connections.discard(websocket)

        logger.info(
            "WebSocket client disconnected. "
            "Active clients=%d",
            len(self._connections),
        )

    # ==========================================================
    # BROADCAST
    # ==========================================================

    async def broadcast(
        self,
        event: dict[str, Any],
    ) -> None:

        if not self._connections:
            return

        message = json.dumps(
            event,
            default=str,
        )

        async with self._lock:
            connections = list(self._connections)

        results = await asyncio.gather(
            *[
                self._send(
                    websocket,
                    message,
                )
                for websocket in connections
            ],
            return_exceptions=True,
        )

        for websocket, result in zip(
            connections,
            results,
        ):

            if isinstance(
                result,
                Exception,
            ):

                logger.warning(
                    "Removing failed WebSocket connection: %s",
                    result,
                )

                await self.disconnect(websocket)

    # ==========================================================
    # SEND TO SINGLE CLIENT
    # ==========================================================

    async def _send(
        self,
        websocket: WebSocket,
        message: str,
    ) -> None:

        await websocket.send_text(message)

    # ==========================================================
    # CONNECTION COUNT
    # ==========================================================

    @property
    def connection_count(self) -> int:

        return len(self._connections)
```

# 6. Why use `asyncio.gather()`?

Imagine 500 frontend clients are connected.

A bad implementation would do:

```python
for client in clients:
    await client.send(...)
```

This effectively processes clients sequentially.

Instead:

```python
await asyncio.gather(
    send(client1),
    send(client2),
    send(client3),
    ...
)
```

The sends can proceed concurrently.

This is important because your alert engine should not become blocked simply because one frontend connection is slow.

# 7. Event contract

This is something we should define **very carefully**.

The frontend shouldn't receive arbitrary Python objects.

Every event should have a predictable structure.

For example:

```json
{
    "event_type": "ALERT_CREATED",
    "event_id": "evt-8d9f",
    "event_timestamp": "2026-08-13T05:20:31.122Z",

    "alert": {
        "alert_id": "ALT-001",

        "device_id": "TEMP-GGN01-L02-MC05-001",
        "device_type": "temperature_process",

        "plant_id": "PLT-GGN-01",
        "machine_id": "MC-LAM-05",

        "rule_id": "TEMP_PROCESS_CRITICAL_HIGH",

        "severity": "CRITICAL",
        "status": "OPEN",

        "value": 225.4,
        "unit": "celsius"
    }
}
```

This gives the frontend everything necessary to display the alert.

# 9. Create an event factory

I recommend another small abstraction:

```text
alert_engine/
│
├── alert_events.py          ← NEW
├── websocket_manager.py
├── alert_manager.py
...
```

`alert_events.py`:

```python
from __future__ import annotations

import uuid
from datetime import datetime, timezone
from typing import Any


def create_alert_event(
    event_type: str,
    alert: Any,
) -> dict:

    return {
        "event_type": event_type,

        "event_id": str(uuid.uuid4()),

        "event_timestamp": (
            datetime.now(timezone.utc).isoformat()
        ),

        "alert": {
            "alert_id": alert.alert_id,

            "device_id": alert.device_id,
            "device_type": alert.device_type,

            "plant_id": alert.plant_id,
            "machine_id": alert.machine_id,

            "rule_id": alert.rule_id,
            "rule_type": alert.rule_type,

            "severity": alert.severity.value,
            "status": alert.status.value,

            "value": alert.current_value,
            "peak_value": alert.peak_value,

            "unit": alert.unit,

            "occurrence_count": (
                alert.occurrence_count
            ),
        },
    }
```

Now the WebSocket manager doesn't need to know anything about your `Alert` implementation.

# 11. Important: database first, WebSocket second

This ordering matters.

Use:

```text
Alert generated
      │
      ▼
Persist alert
      │
      ▼
Publish WebSocket event
```

NOT:

```text
Alert generated
      │
      ▼
WebSocket
      │
      ▼
Database
```

Why?

Suppose:

```text
Alert detected
     ↓
WebSocket sent
     ↓
Backend crashes
     ↓
Database write never happens
```

Now the frontend saw an alert that doesn't exist in history.

That's bad.

Instead:

```text
Alert detected
     ↓
Database commit
     ↓
WebSocket notification
```

Now if WebSocket fails:

```text
Database
    ✓ alert exists

Frontend
    ✗ didn't receive live notification
```

The frontend can recover by fetching active alerts through an API.

This is a much safer architecture.

---

# 12. WebSocket is NOT the source of truth

This is extremely important.

Suppose:

```text
AlertStore
    ↓
ALT-001 = OPEN
```

but:

```text
WebSocket
    ↓
client disconnected
```

The alert still exists.

When the frontend reconnects:

```text
Frontend
   ↓
GET /alerts/active
   ↓
Backend
   ↓
AlertStore
   ↓
ALT-001
```

Then it can synchronize its state.

Therefore:

```text
Database = source of truth
WebSocket = real-time notification
```

# 13. FastAPI endpoint

Eventually your backend can have:

```python
from fastapi import FastAPI, WebSocket

from .websocket_manager import WebSocketManager


app = FastAPI()

websocket_manager = WebSocketManager()


@app.websocket("/ws/alerts")
async def alerts_websocket(
    websocket: WebSocket,
):

    await websocket_manager.connect(websocket)

    try:

        while True:

            # Keep connection alive.
            # Client messages can be handled later.

            await websocket.receive_text()

    except Exception:

        await websocket_manager.disconnect(
            websocket
        )
```

The frontend connects:

```text
ws://backend-host/ws/alerts
```

and waits for events.

For the first implementation, keep it simple.

* authorization
* connection limits
* backpressure
* observability

But those aren't necessary to prove your core architecture.

# 15. A critical scalability consideration

Your concern earlier was:

> What happens if millions of sensor events arrive?

The important thing is that **WebSockets are not processing those sensor events**.

The path should be:

```text
Millions of sensor events
          │
          ▼
     Rule Engine
          │
          │ only abnormal events
          ▼
     Alert Manager
          │
          ▼
      WebSocket
```

Suppose:

```text
10 million readings
```

but only:

```text
500 alerts
```

Then WebSocket sends:

```text
500 events
```

not:

```text
10 million events
```

This is exactly what we want.

---

# 16. Don't send normal readings through WebSocket

This would be a mistake:

```json
{
    "device_id": "TEMP-...",
    "value": 117.2
}
```

for every reading.

Your frontend does **not** need every raw sensor reading through the alert channel.

Instead:

```text
Normal reading
    ↓
Medallion pipeline

Abnormal reading
    ↓
Alert Engine
    ↓
WebSocket
```

If later you want a **live sensor dashboard**, that's a separate streaming requirement.

Don't mix:

```text
Sensor telemetry streaming
```

with:

```text
Alert streaming
```

# 18. One important correction before Part 8

There is one thing I would **not** do in `main.py` yet:

```python
for file in files:
    for row in rows:
        process(row)
```

and have every row execute expensive operations independently.

For your current JSON-based prototype, that's fine for testing, but the architecture should isolate:

```text
Input Adapter
```

from:

```text
Alert Engine
```

So eventually:

```text
JSON Adapter
     │
     ▼
SensorEvent
     │
     ▼
Alert Engine
```

and later:

```text
Kafka Adapter
     │
     ▼
SensorEvent
     │
     ▼
Alert Engine
```

The Alert Engine doesn't care whether the event came from:

```text
JSON
Kafka
MQTT
API
IoT Hub
```

This is what will make your **Part 10 Kafka migration** genuinely clean rather than just changing a few lines in `main.py`.
