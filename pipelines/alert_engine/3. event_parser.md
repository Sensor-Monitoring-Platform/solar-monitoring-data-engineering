## Part 3 — `event_parser.py`

Now we create the **ingestion boundary** of the Alert Engine.

The parser has one very important responsibility:

> **Bad sensor data must produce a rejected/invalid event — it must NOT crash the Alert Engine or stop processing the remaining sensors.**

Your generator will eventually intentionally produce:

* valid readings
* corrupted records
* missing fields
* invalid numeric values
* invalid timestamps
* emergency values
* optional `error_code`
* optional `sensor_health`
* optional `calibration_status`

The parser should handle these safely.

---

# Why this parser is important

Consider your current valid event:

```json
{
    "device_id": "TEMP-GGN01-L01-MC01-001",
    "device_type": "temperature_process",
    "plant_id": "PLT-GGN-01",
    "machine_id": "MC-ASM-01",
    "timestamp": "2026-08-04T05:18:34.215849+00:00",
    "reading": {
        "value": 117.7582,
        "unit": "celsius"
    }
}
```

The result becomes:

```text
ParseResult
    success = True
    event = SensorEvent(...)
```

Then:

```text
SensorEvent
      ↓
RuleEngine
```

---

## But imagine your generator produces this

```json
{
    "device_id": "TEMP-GGN01-L01-MC01-001",
    "device_type": "temperature_process",
    "plant_id": "PLT-GGN-01",
    "machine_id": "MC-ASM-01",
    "timestamp": "NOT-A-TIMESTAMP",
    "reading": {
        "value": 117.7,
        "unit": "celsius"
    }
}
```

We **do not** want:

```python
raise ValueError(...)
```

and then:

```text
💥 Alert Engine dies
```

Instead:

```text
ParseResult
    success = False
    error_code = INVALID_TIMESTAMP
```

The processing loop can then continue:

```text
Record 1 → valid → evaluate
Record 2 → valid → evaluate
Record 3 → corrupted → reject
Record 4 → valid → evaluate
Record 5 → emergency → alert
Record 6 → valid → evaluate
```

This is essential for your use case.

---

# One subtle but important point

The parser **does not decide whether a reading is dangerous**.

For example:

```json
"reading": {
    "value": 250,
    "unit": "celsius"
}
```

is perfectly valid structurally.

The parser says:

> "Yes, this is a valid sensor event."

Then the Rule Engine says:

> "250°C exceeds the configured critical threshold."

That's exactly the separation we want:

```text
                    ┌──────────────────┐
Raw JSON ──────────►│   Event Parser   │
                    └────────┬─────────┘
                             │
                       valid event
                             │
                             ▼
                    ┌──────────────────┐
                    │   Rule Engine    │
                    └────────┬─────────┘
                             │
                    threshold exceeded
                             │
                             ▼
                    ┌──────────────────┐
                    │  Alert Manager   │
                    └──────────────────┘
```

---

# What about corrupted data?

This is where your **two parallel paths** become useful.

Suppose the generator produces:

```json
{
    "device_id": "TEMP-...",
    "timestamp": "garbage",
    "reading": {
        "value": "abc"
    }
}
```

The Alert Engine should **not silently treat this as normal**.

Instead:

```text
RAW EVENT
   │
   ▼
PARSER
   │
   ├── VALID ───────────────► RULE ENGINE
   │
   └── INVALID
          │
          ├── metrics
          ├── error log
          └── invalid-event stream
```

Meanwhile your Medallion pipeline can independently put the malformed record into:

```text
quarantine/
```

This gives you two different purposes:

| Component           | Purpose                                |
| ------------------- | -------------------------------------- |
| Alert Engine parser | Protect real-time alert processing     |
| Bronze validation   | Protect data quality                   |
| Quarantine          | Preserve bad records for investigation |
| Silver              | Produce trusted analytical data        |

---

# One thing I intentionally did NOT do

I did **not** reject:

```json
"sensor_health": "BAD"
```

or:

```json
"calibration_status": "INVALID"
```

inside the parser.

Why?

Because these can be **valid sensor events describing a bad sensor condition**.

For example:

```json
{
    "device_id": "TEMP-001",
    "sensor_health": "BAD",
    "reading": {
        "value": 120
    }
}
```

Structurally this is valid.

The Alert Engine should potentially generate:

```text
SENSOR_HEALTH_DEGRADED
```

or:

```text
SENSOR_FAULT
```

That belongs to the **rule/state layer**, not basic parsing.

This distinction is extremely important for your project.

## Part 4 — `state_manager.py`

This is where we'll solve your earlier question about **unordered batch data and missing readings**.

We cannot simply do:

```python
if missing_count > 60:
    alert()
```

because your input is a batch and may contain timestamps like:

```text
05:00
05:02
05:01
05:04
05:03
```

and potentially multiple batches can arrive out of order.

Instead, the state manager needs to maintain state **per `device_id`**, based on event timestamps rather than arrival order.

It will track things like:

```text
device_id
last_event_timestamp
last_value
last_seen
expected_interval
offline_grace_period
consecutive_invalid_events
sensor_state
```

and distinguish:

```text
ONLINE
   ↓
NO RECENT EVENT
   ↓
SUSPECTED_OFFLINE
   ↓
OFFLINE
   ↓
EVENT RECEIVED
   ↓
RECOVERED
```

That is the piece I'd build next before touching WebSockets or the database, because **alert correctness depends on getting sensor state right first.**
