# Part 6 — `alert_store.py` — Persistence & Alert History

Now we build the **persistence layer**.

This is important because `AlertManager` currently keeps alerts in memory:

```text
AlertManager
    ↓
self._alerts
```

If the process restarts:

```text
💥 memory gone
💥 active alerts gone
💥 history gone
```

That is obviously unacceptable for a real monitoring system.

The `AlertStore` becomes the **persistent source of truth for alert incidents and their history**.

---

# 1. What should we persist?

We should **not store every sensor reading in the alert database**.

Your Medallion pipeline already owns sensor history:

```text
Raw
 ↓
Bronze
 ↓
Silver
 ↓
Gold
```

The Alert Engine should persist **alert/incident information**.

So we have two concepts:

```text
Sensor data
    ↓
Medallion storage
```

and:

```text
Alert events
    ↓
Alert database
```

---

# 2. Recommended database model

For the first implementation, use two tables:

```text
alerts
alert_events
```

### `alerts`

Stores the **current/latest state of an incident**.

### `alert_events`

Stores the **history of changes/events associated with that incident**.

This gives us:

```text
alerts
┌──────────────┐
│ ALT-001      │
│ CRITICAL     │
│ OPEN         │
│ peak = 240   │
└──────┬───────┘
       │
       │ history
       ▼
alert_events
┌──────────────────────┐
│ CREATED              │
│ VALUE_UPDATED        │
│ VALUE_UPDATED        │
│ ACKNOWLEDGED         │
│ VALUE_UPDATED        │
│ RESOLVED             │
└──────────────────────┘
```

This is much better than simply updating one database row and losing the history.

---

# 3. Why `alert_events` matters

Suppose an operator asks:

> "Why was this alert generated?"

We can answer:

```text
10:05:00
TEMP = 215°C
→ CRITICAL_HIGH triggered

10:05:30
TEMP = 218°C

10:06:00
TEMP = 225°C

10:06:10
Operator Ravi acknowledged alert

10:08:00
TEMP = 178°C

10:08:01
Alert resolved
```

This becomes extremely valuable later for:

* incident investigation
* auditability
* false-alert analysis
* MTTR
* alert response time
* AI evaluation
* operational dashboards

# 8. How AlertManager should use AlertStore

We now modify `AlertManager`.

Instead of:

```python
self._alerts = {}
```

being the only source of truth, we'll inject the store:

```python
class AlertManager:

    def __init__(
        self,
        deduplicator,
        alert_store,
    ):
        self.deduplicator = deduplicator
        self.alert_store = alert_store
```

Then when an alert is created:

```python
alert = self.create_alert(...)

self.alert_store.create_alert(alert)
```

When updated:

```python
alert = self.update_alert(...)

self.alert_store.update_alert(alert)
```

When acknowledged:

```python
alert = self.acknowledge(...)

self.alert_store.acknowledge_alert(alert)
```

When resolved:

```python
alert = self.resolve(...)

self.alert_store.resolve_alert(alert)
```

# 9. Very important architecture decision

The database is **not the source of truth for sensor data**.

We have:

```text
                 SENSOR DATA
                      │
          ┌───────────┴───────────┐
          │                       │
          ▼                       ▼
     ALERT ENGINE            MEDALLION
          │                       │
          ▼                       ▼
    Alert Database          Bronze/Silver/Gold
```

The Alert Database answers:

> What incidents happened?

The Medallion system answers:

> What sensor measurements happened?

This separation is extremely important.

---

# 10. What happens when an alert is generated?

Example:

```text
TEMP = 220°C
```

### Alert engine

```text
Rule Engine
    ↓
CRITICAL
    ↓
AlertManager
    ↓
Deduplicator
    ↓
NEW
```

Then:

```text
AlertManager
     │
     ├───────────────► AlertStore
     │                       │
     │                       ▼
     │                 alerts table
     │                       +
     │                 alert_events
     │
     └───────────────► WebSocket Publisher
```

The frontend immediately gets:

```json
{
    "event_type": "ALERT_CREATED",
    "alert_id": "ALT-123",
    "device_id": "TEMP-GGN01-L01-MC01-001",
    "machine_id": "MC-ASM-01",
    "severity": "CRITICAL",
    "status": "OPEN",
    "value": 220.0
}
```

while the database gets the persistent record.

---

# 11. What if the Alert Engine crashes?

Suppose:

```text
10:00 → critical alert
10:01 → engine crashes
10:05 → engine restarts
```

Because we persisted:

```text
alerts
```

the engine can load:

```text
OPEN alerts
```

at startup.

This will become important when we implement startup recovery.

---

# 12. What if the same alert comes back after restart?

This is another reason the persistent store matters.

Without persistence:

```text
Engine restart
    ↓
deduplication memory lost
    ↓
same alert arrives
    ↓
NEW alert created
```

Potentially:

```text
ALT-001
ALT-002
```

for the same physical incident.

Eventually we'll load active alerts from `AlertStore` into the deduplication registry during startup.

So:

```text
Database
   ↓
Startup Recovery
   ↓
AlertManager
   ↓
Deduplicator
```

This will be part of `main.py`.

## One thing I want to keep strict going forward

We **shouldn't jump into WebSockets yet**.

There is one architectural boundary we need first:

```text
AlertManager
       │
       ├── AlertStore
       │
       └── Event Publisher
```

The Event Publisher should be an abstraction, rather than having `AlertManager` directly call WebSocket code.

That lets us eventually do:

```text
                 AlertManager
                      │
                AlertEvent
                      │
                      ▼
               EventPublisher
                 /        \
                /          \
          WebSocket       Kafka
             │              │
             ▼              ▼
         Frontend       Other services
```

This also directly supports your original goal of **replacing the current JSON batch input with Kafka later without rewriting the core alert logic**.
