# Part 8 — `main.py` — Wiring the Alert Engine to Your Current JSON

Now we connect the pieces we have built so far to your **actual generated sensor JSON**.

The most important design decision here is that `main.py` should be an **orchestrator**, not the place where alert logic lives.

It should basically do:

```text
JSON file
   ↓
Input adapter
   ↓
SensorEvent
   ↓
Alert Engine
   ├── Rule Engine
   ├── State Manager
   ├── Deduplication
   ├── Alert Manager
   ├── Alert Store
   └── WebSocket publisher
```

Later:

```text
Kafka
   ↓
Input adapter
   ↓
SensorEvent
   ↓
SAME Alert Engine
```

So we are deliberately creating a boundary now that will make Part 10 easy.

# 4. Create `input_adapter.py`

This is responsible for converting your existing JSON records.

```python
from __future__ import annotations

from datetime import datetime
from typing import Any

from .models import SensorEvent


def _parse_timestamp(
    value: str | None,
) -> datetime | None:

    if not value:
        return None

    return datetime.fromisoformat(
        value.replace("Z", "+00:00")
    )


def parse_sensor_record(
    record: dict[str, Any],
) -> SensorEvent:

    reading = record.get("reading") or {}

    return SensorEvent(
        device_id=record["device_id"],
        device_type=record["device_type"],

        plant_id=record["plant_id"],
        machine_id=record["machine_id"],

        timestamp=_parse_timestamp(
            record["timestamp"]
        ),

        value=reading.get("value"),

        unit=reading.get("unit"),

        firmware_version=record.get(
            "firmware_version"
        ),

        quality_flag=record.get(
            "quality_flag"
        ),

        ingestion_timestamp=_parse_timestamp(
            record.get("ingestion_timestamp")
        ),

        source_file_name=record.get(
            "source_file_name"
        ),
    )
```

# 5. Important: corrupted records

This adapter should **not silently repair corrupted data**.

For example:

```json
{
  "device_id": "...",
  "reading": {
    "value": "INVALID"
  }
}
```

Do not do:

```python
float("INVALID")
```

and pretend everything is okay.

Instead, the adapter should reject malformed events.

Create:

```python
class InvalidSensorEvent(Exception):
    pass
```

Then:

```python
def parse_sensor_record(
    record: dict[str, Any],
) -> SensorEvent:

    required_fields = [
        "device_id",
        "device_type",
        "plant_id",
        "machine_id",
        "timestamp",
    ]

    missing = [
        field
        for field in required_fields
        if field not in record
    ]

    if missing:
        raise InvalidSensorEvent(
            f"Missing required fields: {missing}"
        )

    reading = record.get("reading")

    if reading is None:
        raise InvalidSensorEvent(
            "Missing reading object"
        )

    value = reading.get("value")

    if value is not None:

        try:
            value = float(value)

        except (TypeError, ValueError) as exc:

            raise InvalidSensorEvent(
                f"Invalid reading value: {value!r}"
            ) from exc

    return SensorEvent(
        device_id=record["device_id"],
        device_type=record["device_type"],
        plant_id=record["plant_id"],
        machine_id=record["machine_id"],
        timestamp=_parse_timestamp(record["timestamp"]),
        value=value,
        unit=reading.get("unit"),
        firmware_version=record.get("firmware_version"),
        quality_flag=record.get("quality_flag"),
        ingestion_timestamp=_parse_timestamp(
            record.get("ingestion_timestamp")
        ),
        source_file_name=record.get("source_file_name"),
    )
```

This distinction is important:

```text
Malformed event
     ↓
Input validation
     ↓
Rejected / logged
```

versus:

```text
Valid event
     ↓
Alert evaluation
```

# 6. Where does `quality_flag` fit?

This is one of the important questions you raised earlier.

Suppose the generator produces:

```json
{
  "value": 225,
  "quality_flag": "CORRUPTED"
}
```

The Alert Engine should **not blindly treat 225 as a real physical measurement**.

Your event processing should therefore have an early gate:

```text
SensorEvent
    ↓
Is event structurally valid?
    │
    ├── NO → reject
    │
    └── YES
          ↓
     quality_flag
          │
          ├── INVALID/CORRUPTED
          │       ↓
          │    Don't trigger
          │    physical alert
          │
          └── OK
                  ↓
             Rule Engine
```

But there is a subtlety.

A corrupted sensor event can itself be useful for a **sensor-health alert**.

For example:

```text
quality_flag = CORRUPTED
```

should not cause:

```text
🔥 MACHINE ON FIRE
```

but could cause:

```text
⚠️ SENSOR DATA QUALITY DEGRADED
```

That is a different rule category.

# 7. Therefore, classify rules

Your Alert Engine should eventually distinguish:

```text
PHYSICAL
    Temperature
    Pressure
    Vibration
    Smoke
    Current

DATA_QUALITY
    Corrupted reading
    Invalid unit
    Missing value

SENSOR_HEALTH
    Sensor offline
    Excessive missing readings
    Calibration expired
    Sensor malfunction

    Input source unavailable
```

This is much cleaner than putting everything into:

```python

```

# 9. Reading JSONL

Your sample shows multiple JSON objects one after another.

That is effectively JSON Lines / NDJSON.

So create an input reader:

```python
from __future__ import annotations

import json
from pathlib import Path
from typing import Iterator


def read_json_lines(
    path: str | Path,
) -> Iterator[dict]:

    path = Path(path)

    with path.open(
        "r",
        encoding="utf-8",
    ) as file:

        for line_number, line in enumerate(
            file,
            start=1,
        ):

            line = line.strip()

            if not line:
                continue

            try:

                yield json.loads(line)

            except json.JSONDecodeError as exc:

                print(
                    f"Invalid JSON at "
                    f"{path}:{line_number}: {exc}"
                )
```

# 10. Process one record at a time

This is exactly where your original concern about batch data becomes relevant.

We don't need:

```text
Read 10 million rows
       ↓
Store everything in memory
       ↓
Evaluate everything
       ↓
Send alerts
```

Instead:

```text
Read record
    ↓
Normalize
    ↓
Evaluate
    ↓
Generate alert if required
    ↓
Persist
    ↓
Publish
    ↓
Next record
```

For the prototype:

```python
for record in read_json_lines(file):

    try:

        event = parse_sensor_record(record)

        await process_event(event)

    except InvalidSensorEvent as exc:

        logger.warning(
            "Invalid sensor event: %s",
            exc,
        )
```

This gives you incremental processing.

# 11. But there's an important optimization

You asked earlier:

> Won't millions of if/else statements be slow?

Yes, if you design the engine poorly.

Don't do:

```python
if temperature:
    ...
elif vibration:
    ...
elif pressure:
    ...
elif current:
    ...
elif smoke:
    ...
```

for every rule.

Instead build a rule registry.

For example:

```python
RULES = {
    "temperature_process": temperature_rules,
    "temperature_ambient": ambient_temperature_rules,
    "vibration": vibration_rules,
    "pressure": pressure_rules,
    "current_draw": current_rules,
    "smoke_alarm": smoke_rules,
}
```

Then:

```python
rules = RULES.get(event.device_type)

for rule in rules:
    evaluate(rule, event)
```

This scales much better and is also metadata-driven.

# 12. Even better: precompile rules

Eventually:

```text
sensors.yml
     ↓
Rule Loader
     ↓
Compiled Rule Registry
```

For example:

```python
compiled_rules = {
    "temperature_process": {
        "warning_high": 190,
        "critical_high": 210,
        "warning_low": 50,
        "critical_low": 40,
    },

    "smoke_alarm": {
        "warning_high": 100,
        "critical_high": 200,
    },

```

Then evaluation becomes extremely cheap:

```python
thresholds = compiled_rules[event.device_type]

if event.value >= thresholds["critical_high"]:
    ...
```

No YAML parsing happens per event.

# 13. `main.py` skeleton

Now the orchestrator looks like:

```python
from __future__ import annotations

import asyncio
import logging
from pathlib import Path

from .alert_store import AlertStore
from .alert_manager import AlertManager
from .deduplication import AlertDeduplicator
from .input_adapter import (
    InvalidSensorEvent,
    parse_sensor_record,
)
from .rule_engine import RuleEngine
from .state_manager import SensorStateManager
from .websocket_manager import WebSocketManager


logging.basicConfig(
    level=logging.INFO,
)

logger = logging.getLogger(__name__)


class AlertEngineApplication:

    def __init__(self):

        self.alert_store = AlertStore(
            "data/alerts.db"
        )

        self.websocket_manager = (
            WebSocketManager()
        )

        self.deduplicator = (
            AlertDeduplicator()
        )

        self.state_manager = (
            SensorStateManager()
        )

        self.rule_engine = RuleEngine()

        self.alert_manager = AlertManager(
            alert_store=self.alert_store,
            event_publisher=self.websocket_manager,
            deduplicator=self.deduplicator,
        )

    async def process_record(
        self,
        record: dict,
    ):

        try:

            event = parse_sensor_record(
                record
            )

        except InvalidSensorEvent as exc:

            logger.warning(
                "Rejected sensor event: %s",
                exc,
            )

            return

        # ----------------------------------------------------
        # State update
        # ----------------------------------------------------

        self.state_manager.update(
            event
        )

        # ----------------------------------------------------
        # Rule evaluation
        # ----------------------------------------------------

        evaluations = (
            self.rule_engine.evaluate(
                event
            )
        )

        # ----------------------------------------------------
        # Alert management
        # ----------------------------------------------------

        for evaluation in evaluations:

            await self.alert_manager.process(
                evaluation
            )
```

# 17. One more important point: batch ordering

Your original concern was:

> The batch contains mixed timestamps and sensors without ordering.

Correct.

**Do not assume input ordering.**

For example, you may receive:

```text
05:20:30 TEMP
05:19:00 VIBRATION
05:20:00 TEMP
05:18:30 PRESSURE
05:21:00 TEMP
```

The Alert Engine therefore needs to distinguish:

```text
event timestamp
```

from:

```text
processing timestamp
```

Your existing schema already gives us:

```text
timestamp
ingestion_timestamp
```

We should additionally generate inside the engine:

```text
processed_at
```

So:

```text
event_timestamp
    = when sensor measurement happened

ingestion_timestamp
    = when data entered the system

processed_at
    = when Alert Engine evaluated it
```

Then we can calculate:

```text
processing_latency
=
processed_at - ingestion_timestamp
```

and:

```text
end_to_end_latency
=
processed_at - event_timestamp
```

These metrics will become very useful in Part 9.

# 18. Late events

Suppose:

```text
event A
timestamp = 05:20
```

arrives first.

Then:

```text
event B
timestamp = 05:18
```

arrives later.

We should **not throw B away automatically**.

The Alert Engine can evaluate B, but stateful rules need to understand that B is a late event.

Eventually we can classify:

```text
ON_TIME
LATE
TOO_LATE
```

using a configurable tolerance.

This is particularly important for your future Kafka implementation.

# 19. What the Alert Engine should ignore

The Alert Engine should **not become a second Medallion pipeline**.

It should not perform:

```text
❌ schema evolution
❌ extensive cleansing
❌ joins across millions of historical records
❌ analytical aggregations
❌ dimensional modelling
❌ BI transformations
```

Its job is:

```text
                    ALERT ENGINE
                         │
       ┌─────────────────┼─────────────────┐
       │                 │                 │
   Thresholds        State/Time        Sensor health
       │                 │                 │
       ▼                 ▼                 ▼
    Critical          Missing          Offline
    Warning           readings         calibration
    Anomaly           patterns          failures
```

The Medallion pipeline remains responsible for the **authoritative analytical history**.
