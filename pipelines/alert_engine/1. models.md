## Part 1 — `models.py`

Let's build the contracts first. The goal is that **every other Alert Engine component works with these models instead of passing around loose dictionaries**.

For your current project, I'd use Python `dataclasses` rather than introducing Pydantic immediately. Since the engine will later sit behind FastAPI, we can introduce Pydantic at the API boundary if needed.


# Why these models matter

There are several important design decisions here.

## 1. `SensorEvent` represents one incoming reading

Your current JSON:

```json
{
    "device_id": "TEMP-GGN01-L01-MC01-001",
    "device_type": "temperature_process",
    "plant_id": "PLT-GGN-01",
    "machine_id": "MC-ASM-01",
    "timestamp": "2026-08-04T05:18:34.215849+00:00",
    "reading": {
        "value": 117.7582,
        "unit": "celsius"
    }
}
```

will eventually become:

```python
SensorEvent(
    device_id="TEMP-GGN01-L01-MC01-001",
    device_type="temperature_process",
    plant_id="PLT-GGN-01",
    machine_id="MC-ASM-01",
    timestamp=...,
    reading_value=117.7582,
    reading_unit="celsius",
)
```

This means the rest of the engine doesn't need to know the original JSON structure.

---

# 2. Why `error_code`, `calibration_status`, `sensor_health` are optional

This connects directly to the concern you raised earlier.

Your generator may eventually produce:

```json
{
    "device_id": "...",
    "error_code": "TEMP_SENSOR_FAULT",
    "calibration_status": "VALID",
    "sensor_health": "GOOD",
    "reading": {
        "value": 120
    }
}
```

But your current generator doesn't necessarily produce those fields for every event.

Therefore:

```python
error_code: Optional[str] = None
```

means:

> The Alert Engine understands these fields if they exist, without making them mandatory for every sensor event.

Later, we can define which sensor types actually require them.

---

# 3. `SensorRuntimeState` is different from metadata

This distinction is **very important**.

Your YAML says:

```yaml
offline_grace_period_seconds: 60
```

That is **configuration**.

The runtime state says:

```python
SensorRuntimeState(
    device_id="VIB-GGN01-L01-MC01-001",
    state=SensorState.ONLINE,
    last_event_timestamp=...,
    last_value=2.3
)
```

That is **what is happening right now**.

So:

```text
sensors.yml
     │
     │ configuration
     ▼
Alert Engine
     │
     │ runtime state
     ▼
SensorRuntimeState
```

Do not put runtime state into `sensors.yml`.

---

# 4. Why `AlertRule` is separate from `SensorEvent`

Suppose:

```text
temperature_process
```

has:

```text
WARNING > 190
CRITICAL > 210
```

That means one event:

```text
temperature = 215
```

can be evaluated against multiple rules.

Conceptually:

```text
SensorEvent
     │
     ├── TEMP_HIGH_WARNING
     │
     └── TEMP_HIGH_CRITICAL
```

The rule engine decides which rule actually triggered.

This is much cleaner than embedding the logic inside the event.

---

# 5. `RuleEvaluation` is deliberately separate from `Alert`

This distinction is subtle but extremely useful.

Suppose:

```text
temperature = 215
```

The rule engine says:

```text
CRITICAL
```

That is an **evaluation**.

It doesn't necessarily mean we create a new database alert.

There might already be:

```text
ALERT-123
OPEN
```

for the same condition.

So:

```text
SensorEvent
      ↓
RuleEvaluation
      ↓
AlertManager
      ↓
CREATE / UPDATE / IGNORE / RESOLVE
```

This separation prevents the rule engine from becoming responsible for database state.

---

# 6. `Alert` represents persistent state

For example:

```text
ALERT-123
```

might remain:

```text
OPEN
```

for 15 minutes while hundreds of sensor readings arrive.

The first reading:

```text
215°C
```

creates:

```text
occurrence_count = 1
```

Then:

```text
216°C
218°C
221°C
219°C
```

don't create four more alerts.

Instead:

```text
occurrence_count = 5
last_seen_timestamp = latest event
trigger_value = latest value
```

Same alert.

---

# 7. `AlertEvent` is different again

This is the **notification/event contract**.

For example:

```text
ALERT_CREATED
```

can go to:

```text
WebSocket
Kafka
Redis
frontend
logging
monitoring
```

without exposing the internal rule evaluation implementation.

So our architecture becomes:

```text
                 SensorEvent
                     │
                     ▼
              ┌──────────────┐
              │ Rule Engine  │
              └──────┬───────┘
                     │
                     ▼
              RuleEvaluation
                     │
                     ▼
             ┌───────────────┐
             │ Alert Manager │
             └───────┬───────┘
                     │
                     ▼
                  Alert
                     │
                     ▼
                AlertEvent
                 /       \
                /         \
               ▼           ▼
          Alert DB      WebSocket
```

This separation will make the eventual system much easier to maintain.

# One correction before Part 2

There's one thing I would **not** implement yet:

```python
RuleOperator
```

with arbitrary expressions like:

```text
"value > 210"
"value < 40"
```

and then dynamically execute strings.

**Do not use `eval()`** for this.

We'll implement a safe operator-dispatch mechanism in `rule_engine.py`:

```python
OPERATORS = {
    RuleOperator.GREATER_THAN: lambda value, threshold: value > threshold,
    RuleOperator.LESS_THAN: lambda value, threshold: value < threshold,
    ...
}
```

That gives us dynamic metadata-driven rules without turning configuration into executable Python.
