# Bronze Layer Design

## Overview

The Bronze layer is the first processing stage of the Medallion Architecture.

Its responsibility is to convert raw IoT telemetry into a trusted, queryable dataset while preserving every original record and maintaining complete auditability.

Unlike later layers, the Bronze layer **does not perform business transformations**. It focuses solely on technical validation, schema enforcement, metadata enrichment, and lineage.

---

# Objectives

The Bronze layer is responsible for:

- Schema enforcement
- Schema evolution
- JSON parsing
- Metadata validation
- Data type validation
- Timestamp validation
- Unit validation
- Audit column generation
- Record lineage
- Idempotent ingestion
- Corrupt record isolation
- Processing metrics

Business rules such as machine health scoring or alert generation are intentionally deferred to later layers.

---

# Input

The Bronze pipeline consumes raw NDJSON files generated by the IoT Sensor Simulator.

Directory structure:

```text
raw/
└── year=2026/
    └── month=08/
        └── day=04/
            └── hour=05/
                ├── batch_001.json
                ├── batch_002.json
                └── ...
```

Each file contains one JSON object per line (NDJSON format).

---

# Output

Validated records are written as partitioned Parquet files.

```text
bronze/
└── year=2026/
    └── month=08/
        └── day=04/
            └── hour=05/
                ├── plant_id=PLT-GGN-01/
                │      └── part-00001.parquet
                │
                └── plant_id=PLT-CHN-01/
                       └── part-00002.parquet
```

Parquet is chosen because it provides:

- Columnar storage
- Compression
- Predicate pushdown
- Partition pruning
- Efficient analytical queries
- Compatibility with Spark, DuckDB and modern query engines

# Schema Enforcement

Every incoming record must conform to the expected schema.

Expected fields include:

```text
device_id
device_type
plant_id
machine_id
timestamp
reading_value
reading_unit
quality_flag
```

Records that violate the expected schema are quarantined.

---

# Schema Evolution

The pipeline supports backward-compatible schema evolution.

Example

Old record

```json
{
    "device_id": "...",
    "reading": "..."
}
```

New firmware

```json
{
    "device_id": "...",
    "error_code": "TEMP_SENSOR_FAULT",
    "calibration_status": "VALID",
    "sensor_health": "GOOD",
    "reading": "..."
}
```

Expected behavior

- Existing data remains valid
- New nullable column is introduced
- Older records receive NULL values
- Pipeline execution continues successfully

The arrival of new optional fields must never cause pipeline failure.


The sensor doesn't know:
- machine health
- alert level
- health score
- anomaly
- maintenance required

Those are our software's conclusions and thus need new fields like error_code, sensor health, etc.

```json
"error_code": "TEMP_SENSOR_FAULT",
"calibration_status": "VALID",
"sensor_health": "GOOD",
```
Suppose six months later the sensor manufacturer releases firmware v2.0.

These values will be sent by the devise firmware itself

Bronze's job is simply:
- accept new columns
- evolve schema
- store them

Bronze does not ask: Is sensor_health actually GOOD?


```
Silver observes:

Last 50 readings

↓

No drift

↓

No flatline

↓

No missing values

↓

No excessive noise



Silver derives:

sensor_health = GOOD

* Much better for our Feature Engineering task.
```

# Metadata Validation

Every incoming record is validated against the metadata repository.

Validation includes:

- Device exists
- Plant exists
- Machine exists
- Device belongs to machine
- Firmware version is recognized

Metadata source

```text
devices.yaml
```

Records referencing unknown devices are quarantined.

---

# Sensor Configuration Validation

Each device type is validated against the sensor metadata.

Metadata source

```text
sensor_config.yaml
```

Validation includes:

- Device type exists
- Expected measurement unit
- Sampling configuration
- Threshold configuration

Unknown sensor types are rejected.

---

# Data Type Validation

Examples

Reject

```text

```

Reject

```text

```

Reject

```text

```

Only valid data types are accepted.


Rejected examples


Reason

Future timestamp

---

```text
2015-01-01T00:00:00Z
```

Reason

Excessively old timestamp

Allowed tolerance

```text
±5 minutes
```

(configurable)

---

# Unit Validation

Measurement units must match metadata.

Example

Metadata

```text
temperature_process → celsius
```

Incoming record

```text
fahrenheit
```

Result

Record quarantined

---

# Duplicate Detection

To ensure idempotent ingestion, every record receives a deterministic hash.

Hash inputs

```text
device_id
timestamp
reading_value
```

Algorithm

```text
SHA-256
```

Duplicate hashes are ignored during ingestion.

# Audit Columns

The Bronze pipeline enriches every valid record with operational metadata.

| Column | Purpose |
|----------|----------|
| processing_timestamp | Processing time |
| processing_job_id | Pipeline execution identifier |
| bronze_version | Pipeline version |
| record_hash | Idempotency |
| source_file_name | Data lineage |

These fields enable complete traceability.

# Corrupt Record Handling

Invalid records are never discarded.

Instead, they are written to a quarantine dataset.

Directory

```text
bronze_quarantine/
└── year=YYYY/
    └── month=MM/
        └── day=DD/
```

Schema

| Column |
|----------|
| raw_record |
| error_reason |
| source_file |
| processing_timestamp |
| processing_job_id |

---

```text
INVALID_JSON

INVALID_DATA_TYPE

INVALID_TIMESTAMP

INVALID_UNIT

INVALID_FIRMWARE

DUPLICATE_RECORD
```

# Idempotent Processing

Reprocessing the same raw file must never create duplicate Bronze records.

The pipeline achieves this using:

- Record hashing
- Processed file log
- Pipeline checkpoints

This allows safe retries after failures.

---

# File Lineage

Every processed file generates a processing log.

Example

| File | Records | Valid | Corrupt | Duration |
|------|---------|--------|----------|----------|
| batch001.json | 500 | 497 | 3 | 2.1 sec |

This information supports operational monitoring and debugging.

---

# Partition Strategy

Bronze data is partitioned using:

```text
year
month
day
hour
plant_id
```

Partitioning by `device_id` is intentionally avoided to prevent excessive small files.

---

# Processing Metrics

Each pipeline execution publishes operational metrics.

| Metric | Description |
|----------|-------------|
| files_processed | Number of files processed |
| records_processed | Total input records |
| records_written | Valid Bronze records |
| records_quarantined | Invalid records |
| duplicate_records | Duplicate records skipped |
| schema_evolution_events | New columns detected |
| processing_duration_seconds | Pipeline execution time |

These metrics enable monitoring and SLA reporting.

# Responsibilities

The Bronze layer **must**:

- Preserve original data
- Enforce technical correctness
- Maintain complete auditability
- Support schema evolution
- Isolate corrupt records
- Publish operational metrics

The Bronze layer **must not**:

- Perform business transformations
- Calculate KPIs
- Generate reports
- Compute machine health scores
- Trigger business alerts

Those responsibilities belong to the Silver, Gold, and Alert Engine components.
